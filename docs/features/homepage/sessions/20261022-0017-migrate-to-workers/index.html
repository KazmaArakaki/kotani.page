PHP から Workers へ移行する

state: done feature: homepage

小谷はり灸所のホームページは、1枚の HTML を返すために PHP と CakePHP と MySQL を動かしていた。 この組み合わせのうち、患者さんの目に届いているのはテンプレート2枚ぶんの出力だけである。 それなら、出力そのものを静的ファイルにして置けば済むはずだ。

ただ、確かめてみると、旧サイトは見た目以上のことをしていた。 存在しない URL をトップへリダイレクトし、怪しいアクセスを DB に記録して IP を締め出していた。 どれを持っていき、どれを手放すかを、このセッションで決めた。

NEXT このセッションは完了した。次は優先度「高」の課題 JSON-LD で木曜が営業日 を直す。

決めたこと

#問い決定理由
1なぜリプレイスするかサーバー費用と保守の手間を減らす。見た目と内容は変えない動的な処理がなく、PHP をやめるだけで軽くなる。デザイン刷新や更新の仕組みは別セッション
2元ファイルをどこから取るか旧リポジトリを clone（kotani.page.org/）隠れたリダイレクトや設定まで確認できる。実際に 302 リダイレクトが見つかった
3Cloudflare 上の載せ方Workers の Static Assetsファイルを置くだけで配信でき、あとからコードも足せる
4ビルド工程入れない。素の HTML を手で書く依存を増やさないことが、そのまま保守の軽さになる
5ドメインの切り替えDNS はすでに Cloudflare。workers.dev プレビューで確認してから Custom Domain を付ける本番に触る前に、旧サイトと見比べられる
6webroot/ のどれを持っていくか使っているもの全部と、空ファイル3つ。CakePHP の初期ファイルは捨てる同じ URL が同じ内容を返す状態を保つ
7存在しない URL404.html を 404 で返す（旧サイトは 302 でトップへ飛ばしていた）検索エンジンに正しく伝わる。旧サイトとの違いは意図した差分として扱う
8ヘルスチェック静的ファイル public/healthcheck に OK と書き、_headers で Content-Type を旧サイトと揃えるコードを書かずに済む。叩いているのは GAS の定期実行。_headers は実装中に追加（下記）
9既存の不具合移行では直さない。課題に記録する移行の確認を「旧サイトと差分なし」の一点にしぼる
10新しいコードの置き場所/workspaces/kotani-page 直下を新リポジトリにする旧ソースを参照専用としてはっきり分けられる
11デプロイ手元から pnpm run deploy更新頻度が低く、CI の保守を増やしたくない
12不正アクセスブロック機能もデータも移行しない。旧 DB は消さずに残す静的配信なら変な URL を叩かれても害がない。今回の作業で消えるデータはない

全体のどこに位置づくか

kotani.page のトップページ配信は、このプロジェクトのただ一つの機能である。 今回は、その機能の中身（ページの内容）を変えずに、土台だけを差し替える。

旧サイトで動いていたものは、トップの描画、/healthcheck、API、エラー処理と不正アクセスブロックの4つに分かれる。 残すのは前の2つだけで、どちらも静的ファイルで返せる。 後ろの2つは、静的配信になると守る対象そのもの（PHP とその脆弱性）がなくなる。

内容の誤りもいくつか見つかった。 ただし、ここで直すと「移行で変わった部分」と「修正で変わった部分」の区別がつかなくなる。 移行が正しくできたかを確かめる方法は、旧サイトの HTML と新サイトの index.html を比べて差分がないことの一点にしたい。 誤りは課題に回し、切り替えのあとで直す。

  • main（Worker のスクリプト）を書かない。assets だけの Worker は、リクエストを静的ファイルの配信だけで処理する。

  • routes は切り替え当日まで入れない。最初のデプロイで本番ドメインを奪わないためである。
  • html_handling は既定の auto-trailing-slash のまま。/index.html は / へ寄せられる。

index.html への変換規則

旧テンプレート templates/layout/default.php と templates/Home/index.php の2枚を、1枚の素の HTML に展開する。 header.php と footer.php は0バイトなので、展開しても何も入らない。 テンプレートの PHP は、次の表のものしか使っていない。

旧テンプレートの書き方新しい index.html での書き方なぜ
<?= __('文字列') ?>文字列翻訳ファイルがなく、引数をそのまま返していた
implode('', [sprintf('<p>%s</p>', __('…')), …])<p>…</p> を並べる改行なしで連結されるので、出力に合わせて改行も入れない
$this->Url->image('x.jpg')/img/x.jpgfullBase なしは相対パスを出力していた
$this->Url->image('x.jpg', ['fullBase' => true])https://kotani.page/img/x.jpgJSON-LD の image と logo
$this->Url->assetUrl('x.pdf', ['pathPrefix' => 'pdf/'])/pdf/x.pdfけんこかわら版の8件
$this->Url->build(['?' => false], ['fullBase' => true])https://kotani.page/og:url と canonical。トップ以外のページがないので固定値になる
sprintf('data:image/svg+xml;charset=utf8,%s', rawurlencode(implode(' ', [...])))SVG を空白で連結し、RFC 3986 でパーセントエンコードした data URICSS のアイコン（矢印、ピン、徒歩、電話）。設計時の調査で見落とし、変換中に見つけた
$this->append('css') / append('script') / fetch(...)それぞれの <style> と <script> を、レイアウトの fetch 位置にそのまま置くレイアウトとテンプレートの2枚を1枚に展開する

変換が正しいかどうかは、本番の HTML と比べて確かめる。 比べる相手は curl https://kotani.page/ の出力で、空白と改行を正規化したうえで差分ゼロを合格とする。

404.html

存在しない URL には、院名と「トップページへ戻る」ボタンだけのページを返す。 トップと同じフォント、文字色、アクセント色を使い、電話ボタンと同じ形のボタンを置く。 見本は ページ見本の 404 にあり、そこにある 404.html をそのまま public/404.html にする。

旧サイトはトップへ 302 で飛ばしていたので、この扱いは意図した差分になる。 404 ページには Google アナリティクスを入れない。旧サイトではリダイレクト先のトップとして数えられていたので、数字の連続性はもともとない。

/healthcheck

public/healthcheck に OK（改行なし）を置く。 叩いているのは GAS の定期実行で、UrlFetchApp の応答コードと本文で判定しているはずである。

拡張子がないので、そのままでは Content-Type が付かなかった（wrangler dev で確認）。 Static Assets が読む public/_headers に次の2行を書くと、旧サイトと同じ text/plain; charset=UTF-8 になる。 _headers 自体は配信されず、/_headers は 404 になる。 

/healthcheck
  Content-Type: text/plain; charset=UTF-8

auto-trailing-slash が拡張子のないパスを HTML ページとして扱う心配もあったが、/healthcheck は 200 と OK を返した。 GAS からは、workers.dev へのデプロイ後に一度叩いてもらう。

旧サイトから変わる挙動

次の3点は、差分があってよいと決めたもの。robots.txt の charset や sitemap.xml の型（text/xml から application/xml）のような、配信基盤が付ける型の細かな違いは含めない。これ以外の差分は移行の誤りとして扱う。

URL や挙動旧サイト新サイト
存在しない URL（/nope、/pages/*、/api/* など）302 で https://kotani.page/ へ404 と 404.html

実装の手順

  1. done dev container に Node.js を入れる。今の .devcontainer/Dockerfile には Node がなく、wrangler が動かない（devcontainer.json に ghcr.io/devcontainers/features/node:1 を "version": "lts" で足す。15分）。当初 apt の Node 22 を入れたが、2027-04 にサポートが終わるため 24 に入れ替えた
  2. done git init し、.gitignore、package.json、wrangler.jsonc を置く（10分）
  3. done webroot/ から持っていくファイルを public/ へコピーする（10分）
  4. done 変換規則に沿って public/index.html を書き、本番 HTML との差分ゼロを確かめる（1時間）。テンプレートを機械的に展開する変換スクリプトで生成し、空白を正規化した比較で差分ゼロを確認した
  5. done public/404.html と public/healthcheck を置き、pnpm dev で確かめる（20分）。public/_headers も置いた
  6. done pnpm run deploy で workers.dev に出し、下の「切り替え前の確認」をすべて通す（30分）。2026-10-22 に https://kotani-page.twi1ightmessenger1988.workers.dev へデプロイ済み。認証は .devcontainer/.env の CLOUDFLARE_API_TOKEN（dev container がポートを公開しておらず、wrangler login のコールバックが届かないため）。GAS からの確認と目視も開発者が済ませた

切り替え前の確認

  • ✅ workers.dev の / と本番の HTML の差分がない
  • ✅ index.html が参照する画像27件と PDF 8件が、すべて 200 で返る（public/ の全ファイルでも確認）
  • ✅ /healthcheck が 200、text/plain; charset=UTF-8、OK を返す
  • ✅ GAS のスクリプトを workers.dev の URL に向けて一度実行し、成功と判定される
  • ✅ /.well-known/apple-app-site-association が返る（ドットで始まるディレクトリが配信対象から外れていないか）
  • ✅ /nope が 404 と 404.html を返す
  • Google マップの埋め込みは、API キーのリファラー制限で workers.dev では出ない可能性がある。出なくても不合格にしない
  • ✅ ブラウザで開き、旧サイトと見た目が同じことを目視する

切り替えの手順

  1. done Cloudflare の DNS で、今の kotani.page のレコード（種類、値、プロキシ設定）を控える。戻すときに使う
  2. wrangler.jsonc に routes を足して pnpm run deploy する。既存のレコードがあると Custom Domain の作成が拒否されることがあるので、そのときはダッシュボードの指示に従って既存レコードを置き換える
    done 実際には、wrangler が付ける「既存レコードを上書きする」指定があっても、API が Hostname 'kotani.page' already has externally managed DNS records（code 100117）で拒否した。そこで A レコードを API で削除し、直後に pnpm run deploy した。失敗したら A レコードを自動で作り直すようにして実行した。2026-10-22 01:09:28 JST に削除し、01:09:35 に Custom Domain の作成が完了、01:09:44 に 200 を確認。止まっていたのは長くても16秒ほど
  3. 本番の https://kotani.page/ で、切り替え前の確認をもう一度通す（レスポンスヘッダーに x-powered-by がなければ新サイト）
    done HTML の差分なし、x-powered-by なし、/healthcheck は 200 と text/plain; charset=UTF-8 と OK、/nope は 404、public/ の50ファイルはすべて 200。MX の5件、dev.kotani.page、_domainconnect はそのまま残り、apex には Workers が管理する読み取り専用の AAAA 100:: ができた
  4. done GAS の向き先を本番に戻し、次の定期実行が成功することを見届ける
    2026-10-22 に開発者が GAS の URL を https://kotani.page/healthcheck に戻して手動で実行し、成功を確認した

routes を足したデプロイから、workers.dev の URL は 404 になった。wrangler.jsonc で workers_dev を指定していないと、routes があるときは workers.dev が無効になるためである。本番と同じ内容の URL が別にあっても使い道がないので、このままにする。

戻すときは、Worker から Custom Domain を外し、手順1で控えたレコードを作り直す。 旧サーバーは止めずに残してあるので、レコードさえ戻せば元どおりになる。
